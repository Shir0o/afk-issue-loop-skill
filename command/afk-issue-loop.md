Run the AFK issue loop for the current repository. Load the `afk-issue-loop` skill and follow its operating principles and phases exactly:

## Phase 0 — Ground the repo profile
- Read `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md` if present; fall back to canonical labels (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`).
- Note the repo docs to respect: `AGENTS.md`, `CONTEXT.md`, `docs/adr/`, `docs/agents/*.md`, `.out-of-scope/`.
- Determine merge method (`gh repo view --json squashMergeAllowed,...`; prefer squash).
- Determine required checks from `.github/workflows/*` and the ruleset (`gh api repos/<OWNER>/<REPO>/rules/branches/main`).
- If main has any review/merge-queue requirement, run in **orchestrator-merges mode** (the orchestrator squash-merges with `--admin`, then syncs main).
- Check install state (`node_modules` present?).
- **Interruption / In-flight check**: Inspect `.worktrees/issue-*`, active `agent/issue-*` branches, open PRs, and recent session history. Prioritize resuming in-flight issues before pulling new ones from the queue.
- Build the queue from `gh issue list --state open`: in-flight/interrupted issues first, then unlabeled/`needs-triage`, then `ready-for-agent` in dependency order, then skip `needs-info`/`ready-for-human` (report only).
- **Ask user execution mode (default sequential)**: Unless arguments specify (`--parallel`, `--serial`, `--sequential`, or `--concurrency <N>`), ask the user:
  > "Do you want to run issues sequentially (1 agent at a time, cost-minimal; default) or in parallel (specify concurrency limit, e.g. 2 or 3)?"
  If the user does not specify or picks default, use `sequential`. If parallel is chosen without a number, default $N$ to 2.
  Record the selected mode (`sequential` or `parallel`) and concurrency limit $N$.

## Phase 1 — Issue dispatch (sequential or parallel)
- **Sequential mode**: For each queued issue in order, spawn ONE subagent (general), strictly serial, using the skill's subagent prompt template (Fresh prompt for new work, Resume prompt for interrupted issues with diff context). While it runs, do inline `gh` bookkeeping only.
- **Parallel mode (Conflict-Minimizing Issue Selection)**:
  - Select up to $N$ independent issues targeting disjoint file sets or subsystems (e.g. frontend vs backend, distinct endpoints/docs) to prevent merge conflicts and avoid costly re-runs.
  - Never concurrently dispatch issues that modify the same files or shared schemas.
  - Run each subagent in its own isolated worktree (e.g. `.worktrees/issue-<N>`).
- If resuming an interrupted issue: dispatch subagent with the Resume prompt providing existing branch, worktree path, uncommitted/committed diff summary, and remaining tasks. Do not restart from scratch.
- `ready-for-agent` → Branch A (implement): TDD per AGENTS.md, branch `agent/issue-<N>` from fresh origin/main, full gate before push (`npm run typecheck && npm run lint && npm run test:coverage && npm run build`), PR with `Closes #<N>`, `gh pr checks --watch`, ≤3 fix cycles then report blocked. STOP at green — do not merge.
- unlabeled / `needs-triage` → Branch B (triage per the `triage` skill, autonomous; comments prefixed with `> *This was generated by AI during triage.*`).
- Detect duplicate issues (same title/body/author within seconds) and close the emptier inline as `wontfix` with a link comment.

## Phase 2 — After each agent settles
1. Verify the claim with one `gh` call (PR state, issue state, labels, comment). NEVER trust `merged` without verifying.
2. In orchestrator-merges mode: `gh pr merge <pr> --squash --admin`, verify the issue auto-closed, sync main (`git pull --ff-only` in the primary checkout). Orchestrator merges sequentially to keep `main` stable.
3. If an agent died mid-flight (or was interrupted):
   - Inspect the worktree and session logs; recover partial diffs and dispatch with Resume prompt instead of discarding work.
   - If the primary checkout has uncommitted changes, stash them first (`git stash push -m "..."`) and inform the user.
4. Reorder the queue if the merge unblocked dependents; in sequential mode spawn the next subagent, in parallel mode maintain up to $N$ active agents by dispatching the next independent issue (disjoint subsystem). Repeat until empty.

## Phase 3 — Wrap-up
- Close epics/spec parents whose decomposition tickets all merged, with a chain summary comment.
- Report a table of issue → outcome (merged PR #, triaged label, closed, blocked + reason) plus any human decisions waiting on GitHub.

Run the loop continuously until the queue is empty. If the user passed arguments ($ARGUMENTS), honor them (e.g. `--parallel`, `--concurrency 3`, "stop after issue N", or "one issue only").
